# Техническое задание: Telegram-бот для совместного чтения Библии

**Версия:** 1.0  
**Тип проекта:** Telegram-бот для групп с включёнными темами (ветками)  
**Язык интерфейса:** русский  
**Приоритет:** минимальное потребление ресурсов, надёжность, простота сопровождения.

## 1. Цель проекта

Разработать Telegram-бота для христианских групп, который:

1. Ежедневно публикует одну главу Библии в определённую ветку группы.
2. Последовательно проходит выбранную книгу, сохраняя прогресс.
3. После завершения книги прекращает публикации до выбора следующей.
4. Собирает статистику активности участников исключительно в привязанной ветке.
5. Каждое воскресенье вечером публикует отдельные сообщения с топ-3 участников по различным номинациям.
6. Поддерживает команды, подробную справку и полноценное администрирование непосредственно через Telegram.
7. Автоматически возобновляет работу после перезапуска сервера.

Проект должен быть пригоден для постоянной эксплуатации.

## 2. Ограничения инфраструктуры

У заказчика уже есть VPS с 4 ГБ оперативной памяти, установленными Python и MySQL. На сервере работают другие проекты.

**Обязательные требования:**

- Использовать существующие Python и MySQL.
- Не устанавливать PostgreSQL, Redis, Docker, Node.js и другие серверные службы.
- Не заменять и не перенастраивать глобальные компоненты существующих проектов.
- Использовать отдельную базу данных внутри существующего MySQL.
- Python-зависимости устанавливать в изолированное виртуальное окружение.
- Использовать Telegram Long Polling вместо webhook.
- Запускать приложение как один systemd-сервис.
- Не требовать постоянного запуска нескольких Python-процессов.
- Не запускать отдельные планировщики задач.
- Не применять тяжёлые ORM и ненужные инфраструктурные зависимости.
- Не хранить полные тексты сообщений участников.
- Обеспечить умеренное потребление оперативной памяти.

### Предлагаемый стек

- aiogram 3 — Telegram Bot API.

Не создавать дополнительных постоянно работающих сервисов без технической необходимости.

## 3. Поддержка групп и тем

Бот должен работать в Telegram-супергруппах с включёнными темами (forum topics).

При привязке сохранять:

- `chat_id` — идентификатор группы.
- `message_thread_id` — идентификатор ветки.
- Дату привязки.
- Параметры чтения и статистики.

### Привязка

Администратор выполняет `/bind` непосредственно внутри нужной ветки.

Бот проверяет полномочия администратора, сохраняет идентификаторы и подтверждает привязку.

Все дальнейшие публикации глав, отчётов и обычные ответы бота должны отправляться именно в эту ветку.

Сообщения участников из других веток не должны учитываться в статистике.

Если администратор выполняет `/bind` в другой ветке уже настроенной группы, бот запрашивает подтверждение переноса. Старую статистику сохранять, но не смешивать с новой.

Статистика, отчёты, `/stats`, `/mystats` и накопительные показатели относятся к конкретной привязанной ветке, а не ко всей группе. После переноса привязки данные прежней ветки остаются в истории, но не включаются в показатели новой ветки.

Архитектура должна поддерживать несколько групп, каждая со своими независимыми настройками, книгами, расписанием и статистикой.

### Права доступа

Команды изменения настроек доступны только владельцу и администраторам конкретной Telegram-группы.

Владельцем считается создатель Telegram-группы; отдельный глобальный список владельцев в конфигурации не требуется.

Права проверяются через Telegram Bot API, в том числе при взаимодействии с inline-кнопками.

Не использовать простой список администраторов, сохранённый однажды: изменение прав пользователя должно учитываться.

Участники могут пользоваться публичными командами, но не могут изменять параметры чтения.

Административные команды принимаются в привязанной ветке. Исключение — первоначальная привязка и перенос через `/bind`.

Перед эксплуатацией отключить Privacy Mode для бота в BotFather. Бот должен быть администратором группы и иметь право отправлять сообщения в темах, чтобы получать все требуемые сообщения и публиковать главы и отчёты.

Пример:

`GET https://api.midvash.com/v1/synodal/john/3`

Получение целой главы должно происходить по HTTP через отдельный сервисный модуль.

3. Хранить локальный каталог книг с сокращениями, API-slug и количеством глав.
4. Выполнить проверку соответствия локального каталога API.
5. Получать текст главы и информацию об авторстве/лицензии из ответа API.

7. Не публиковать некорректный или пустой ответ.

Использовать поля `data` и `meta` согласно актуальной документации API, а не предполагать структуру ответа.

При публикации корректно указывать перевод и предусмотренные API сведения об авторских правах.

Сокращения должны быть нечувствительными к регистру.

## 5. Ежедневная публикация глав

Администратор выбирает книгу командой:

`/setbook ин`

Бот устанавливает:

- Книга: Евангелие от Иоанна.
- Следующая глава: 1.
- Статус: ACTIVE.

Возможно указать начальную главу:

`/setbook рим 5`

При выборе новой книги необходимо проверять, существует ли она и корректен ли номер главы.

### Расписание

По умолчанию публикация происходит ежедневно в 08:00.

Часовой пояс по умолчанию: `UTC`.

Администратор может изменить время:

`/time 07:30`

Расписание хранить в MySQL.

После выбора книги первая автоматическая публикация происходит в ближайшее запланированное время в будущем.

### Формат сообщения

Пример:

📖 **ЕВАНГЕЛИЕ ОТ ИОАННА**  
**Глава 3 из 21**

1. Текст первого стиха...
2. Текст второго стиха...
3. Текст третьего стиха...

...

💭 Делитесь своими мыслями по прочитанному с тегом #мысль.

📚 Синодальный перевод.

Текст должен быть читабельным, с сохранением абзацев и нумерации стихов.

### Длинные главы

Telegram ограничивает длину обычного сообщения.

Реализовать разбиение главы на несколько сообщений, каждое с учётом ограничения в 4096 символов после форматирования.

- Не разрывать стихи посередине, если возможно.
- При слишком длинном стихе допускается перенос по словам.
- Указывать номер части, например `Часть 1/3`.
- Не дублировать текст.
- Сохранять порядок частей.
- Все части отправлять в одну ветку.

### Прогресс

Следующую главу публиковать только после успешного завершения текущей публикации.

После последней главы книги:

1. Зафиксировать завершение книги.
2. Установить статус `COMPLETED`.
3. Сохранить дату завершения.
4. Отправить одно поздравительное сообщение.

Пример:

🎉 **Мы закончили Евангелие от Иоанна!**

Вместе прочитана 21 глава!

Спасибо всем, кто читал, размышлял и делился мыслями. 📖

🙏 Ожидаем, когда администратор выберет следующую книгу.

После этого не публиковать новые главы до команды `/setbook`.

Бот продолжает собирать статистику и отправлять еженедельные отчёты, даже если чтение завершено.

### Пауза

`/pause` останавливает только ежедневную публикацию глав.

`/resume` восстанавливает расписание.

Во время паузы статистика продолжает собираться, а недельные отчёты отправляются.

После возобновления продолжать с сохранённой главы.

Пропущенные дни не должны автоматически превращаться в массовую отправку нескольких глав.

## 6. Статистика активности

Бот отслеживает сообщения пользователей исключительно в привязанной ветке.

Для каждого подходящего сообщения сохранять:

- Идентификатор группы и ветки.
- Идентификатор сообщения.
- Идентификатор автора.
- Время отправки (UTC).
- Количество слов.
- Количество отдельных слов «я».
- Наличие тега `#мысль`.
- Наличие вопросительного знака.
- Количество слов благодарности.
- Признаки ночного и утреннего сообщения.
- Другие числовые показатели, необходимые для отчётов.

Не сохранять полный текст сообщения.

При получении события редактирования пересчитывать показатели и обновлять ранее сохранённую запись, не создавая дубликат.

Отслеживание удаления произвольных сообщений Telegram Bot API надёжно не гарантирует. Не считать отсутствие такого механизма ошибкой реализации.

### Какие сообщения учитывать

Учитывать:

- Обычные текстовые сообщения.
- Подписи к фото, видео и документам, если они содержат текст.

Исключать:

- Сервисные сообщения.
- Команды управления ботом.
- Сообщения самого бота.
- Сообщения других ботов.
- Медиа без текстовой подписи.
- Сообщения из других веток.
- Анонимные сообщения от имени группы, если нельзя достоверно определить автора.

Статистика должна начинаться с момента активации привязки. Не требуется получать старую историю группы.

## 7. Еженедельные номинации

Реализовать все перечисленные ниже номинации.

Каждую номинацию можно независимо включать или выключать через Telegram-админку.

Для каждой номинации определять трёх лучших участников.

### 7.1. 🗣 Самые болтливые

Количество текстовых сообщений.

Заголовок:

**На этой неделе самыми болтливыми оказались:**

### 7.2. 💡 Мыслители недели

Количество сообщений с тегом `#мысль`.

Правила:

- Регистр игнорировать.
- `#мысль` считать совпадением.
- `#мысль,` считать совпадением.
- `#мысли` не считать.
- Два одинаковых тега в одном сообщении считать одной мыслью.

Заголовок:

**Больше всех размышляли над Писанием:**

### 7.3. 👑 Самые «скромные» — гордецы недели

Подсчитывать самостоятельное слово «я» без учёта регистра.

Использовать Unicode-границы слов.

Примеры:

- `Я думаю, что я понял` → 2.
- `Моя семья` → 0.
- `Я, конечно, согласен` → 1.
- `Яблоко` → 0.

Слова внутри других слов не учитывать.

Заголовок:

**А вот кто чаще всех вспоминал о себе любимом:**

В конце добавить юмористическую пометку:

*Это всего лишь статистика, а не оценка характера! 😁*

### 7.4. ❓ Почемучки недели

Количество сообщений, содержащих вопросительный знак `?`.

Одно сообщение с несколькими вопросительными знаками засчитывается один раз.

Заголовок:

**У кого на этой неделе возникло больше всего вопросов?**

### 7.5. 🌙 Ночные стражи

Количество сообщений, отправленных с 22:00 до 04:59 по местному времени группы.

Заголовок:

**Пока другие спали, эти стражи несли свою службу:**

### 7.6. 🌅 Ранние пташки

Количество сообщений с 05:00 до 07:59.

Заголовок:

**Раньше всех просыпались и писали:**

### 7.7. ❤️ Самые благодарные

Подсчёт отдельных слов благодарности.

Начальный словарь:

- спасибо
- благодарю
- благодарим
- благодарен
- благодарна
- благодарны

Каждое найденное слово считается отдельно.

Словарь должен храниться в конфигурации приложения и легко расширяться.

Заголовок:

**Больше всех делились благодарностью:**

### 7.8. ✍️ Авторы посланий

Количество написанных слов за неделю.

Учитывать Unicode-слова на кириллице и латинице.

Пунктуация не считается словами.

Заголовок:

**Кажется, эти участники могли бы написать целое послание:**

### 7.9. 🌱 Верные в малом

Альтернативное отображаемое название: **Постоянные участники**.

Количество различных дней активности в отчётном периоде.

Если участник написал 100 сообщений в один день, ему засчитывается один день активности.

Если писал в каждый из семи отчётных дней — результат 7/7.

Заголовок:

**А вот кто проявил постоянство и участвовал почти каждый день:**

Эта номинация должна мотивировать регулярное участие, а не огромное количество сообщений.

## 8. Еженедельные отчёты

По умолчанию отправлять каждое воскресенье в 21:00 по часовому поясу группы.

Время можно менять командой:

`/weektime 20:30`

Отчётный период должен составлять семь последовательных суток без пропусков и пересечений, от предыдущего планового отчёта до текущего. Для первого автоматического отчёта после `/bind` началом периода является время привязки; если с момента привязки прошло меньше семи суток, отчёт формируется за фактически накопившийся период. Последующие периоды начинаются в момент завершения предыдущего автоматического отчёта.

Для номинации «Верные в малом» использовать семь последовательных 24-часовых отчётных дней, определяемых границами периода. Это гарантирует максимум 7/7 даже при отправке отчёта в 21:00.

Даты и время начала/окончания периода указывать в заголовке первого отчёта. При изменении расписания не терять промежуточную статистику.

### Формат

Каждую включённую номинацию отправлять отдельным сообщением.

Пример:

🏆 **БОЛТУНЫ НЕДЕЛИ**

На этой неделе самыми болтливыми оказались:

🥇 Андрей — 143 сообщения  
🥈 Мария — 112 сообщений  
🥉 Давид — 87 сообщений

Поздравляем наших победителей! 🎉

### Правила рейтинга

- Сортировать по убыванию значения показателя.
- Выводить не более трёх человек.
- Не выводить участников с нулевым значением.
- Если участвовало меньше трёх человек, показывать только существующих.
- Если по номинации нет данных, пропускать её.
- При равенстве значений использовать стабильный порядок, например время первого засчитанного сообщения и затем Telegram user ID.
- Использовать актуальное отображаемое имя участника.
- Желательно добавлять Telegram-упоминание участника через его ID, если это возможно.
- Экранировать имена при HTML-форматировании.
- Не отправлять повторно уже опубликованный автоматический отчёт.

### Ручной отчёт

`/report` — выводит текущие предварительные итоги.

`/report last` — выводит результаты последнего завершённого периода.

Ручной вызов не должен сбрасывать статистику, изменять расписание или блокировать очередной автоматический отчёт.

Команды ручного отчёта доступны всем участникам в привязанной ветке; они показывают только статистику этой ветки.

## 9. Дополнительные функции

### 9.1. Глава дня

Команда `/today` показывает:

- Название последней опубликованной книги.
- Номер главы.
- Дату публикации.
- Ссылку на первое сообщение главы.

При вызове `/today` не отправлять повторно весь текст главы.

Если глава ещё не публиковалась, показать понятное сообщение.

### 9.2. Общий прогресс

Сохранять:

- Количество завершённых книг.
- Количество успешно опубликованных глав.
- Даты начала и окончания прочитанных книг.
- Историю выбранных книг.

Команда `/progress` показывает общий прогресс группы.

В `/status` отображать текущую книгу, количество прочитанных глав и оставшееся количество.

### Настройка часового пояса

Добавить отдельную настройку часового пояса в Telegram-админке.

**Основные требования:**

1. Внутренний эталон времени — UTC+0.
2. Все временные метки в MySQL сохранять в UTC.
3. Для каждой группы хранить собственный часовой пояс.
4. Часовой пояс по умолчанию — `UTC`.
5. Добавить команду `/timezone` и кнопку «🌍 Часовой пояс» в `/admin`.
6. Поддерживать именованные часовые пояса IANA и числовые смещения UTC.
7. При изменении часового пояса пересчитывать расписание публикаций и отчётов.
8. Команды `/time` и `/weektime` интерпретировать в выбранном часовом поясе.
9. Все временные номинации и отчётные периоды рассчитывать в часовом поясе группы.
10. Поддерживать переходы на летнее и зимнее время для IANA-зон через `zoneinfo`.
11. Не допускать дублирования публикаций при изменении настроек.
12. Изменение часового пояса не должно изменять историю уже опубликованных отчётов.

#### Форматы команды /timezone

Поддерживать следующие варианты:

| Команда | Результат |
|---|---|
| `/timezone 0` | UTC+0 |
| `/timezone 5` | UTC+5 |
| `/timezone +5` | UTC+5 |
| `/timezone -3` | UTC−3 |
| `/timezone UTC+5` | UTC+5 |
| `/timezone UTC-4` | UTC−4 |
| `/timezone +5:30` | UTC+5:30 |
| `/timezone UTC+5:45` | UTC+5:45 |
| `/timezone Asia/Dushanbe` | Часовой пояс Душанбе |
| `/timezone Europe/Moscow` | Часовой пояс Москвы |

**Допустимый диапазон числовых смещений: от UTC−12:00 до UTC+14:00 включительно.**

При выходе за пределы диапазона возвращать понятную ошибку с указанием допустимых значений.

Числовые смещения должны быть фиксированными, без автоматического перехода на летнее время.

Для именованных зон IANA учитывать соответствующие правила переходов.

Команда `/timezone` без аргументов должна показывать текущий часовой пояс и открывать меню выбора.

#### Хранение

В MySQL хранить тип часового пояса (`IANA` или `FIXED`) и его значение.

Примеры:

- `FIXED`, `+05:00`
- `FIXED`, `-03:30`
- `IANA`, `Asia/Dushanbe`

Для фиксированных смещений использовать Python `datetime.timezone` с `timedelta`, для именованных — `zoneinfo.ZoneInfo`.

В `/status` отображать выбранный часовой пояс вместе с расписанием.

**Пример:**

`/timezone +5`

`/time 08:00`

Бот публикует главу ежедневно в 08:00 UTC+5, что соответствует 03:00 UTC.

## 13. Планировщик

Не использовать системный cron как обязательную зависимость и не запускать отдельный worker.

Реализовать асинхронную задачу внутри основного Python-процесса.

Принцип работы:

1. Периодически проверять MySQL на наличие запланированных публикаций.
2. Определять задания, срок которых наступил.
3. Проверять, выполнялось ли задание.
4. Выполнять публикацию.
5. Сохранять результат.
6. При ошибке записывать её и планировать повторную попытку.

Интервал проверки — примерно 30–60 секунд.

Точное время задачи определять по сохранённому расписанию и часовому поясу, не по времени запуска процесса.

### Защита от повторных публикаций

Не допускать повторной отправки одних и тех же глав при обычном рестарте процесса или повторном срабатывании планировщика.

Использовать блокировки и уникальные ключи MySQL, сохранять состояние отправки частей.

Учитывать, что Telegram API и MySQL не поддерживают общую атомарную транзакцию. При сетевом тайм-ауте после фактически успешной отправки невозможно абсолютно гарантировать отсутствие дубля.

В таком случае сохранять состояние неопределённой доставки, не повторять её бесконтрольно и предусмотреть понятное восстановление.

### Сбой VPS

После перезапуска:

- Восстановить настройки.
- Восстановить прогресс чтения.
- Проверить пропущенные задания.
- При необходимости выполнить одну ожидающую публикацию.
- Не отправлять десятки накопившихся глав подряд.
- Не менять номер главы без подтверждённого успешного выполнения.

## 14. Безопасность и конфиденциальность

1. Токен Telegram хранить только в `.env` или защищённом конфигурационном файле.
2. Не включать токены и пароли в Git.
3. Не выводить секреты в логи.
4. Проверять административные права перед каждой изменяющей операцией.
5. Не доверять данным из callback-кнопок без серверной проверки.
6. Защищать SQL-запросы параметризацией.
7. Экранировать пользовательский текст в Telegram HTML.
8. Не сохранять полные сообщения участников.
9. Не предоставлять сторонним участникам статистику администрирования за пределами разрешённой группы.
10. Обрабатывать Telegram Flood Control и ограничения частоты отправки.
11. Ограничить журналы по размеру и сроку хранения.
12. Предусмотреть удаление устаревших подробных метрик, например через 90 дней, сохраняя общую статистику и историю отчётов.

Необходимо учитывать, что Telegram не гарантирует доставку произвольной истории сообщений после длительного отключения бота. Статистика строится только по реально полученным событиям.

## 17. Обработка ошибок

Обязательные сценарии:

- Telegram временно недоступен.
- API Библии возвращает ошибку.
- API возвращает некорректный JSON.
- Указана неизвестная книга.
- Указана несуществующая глава.
- MySQL временно недоступен.
- Бот потерял права в группе.
- Привязанная тема удалена или закрыта.
- Пользователь удалил username или изменил имя.
- Администратор пытается изменить настройки во время публикации.
- Приложение перезапускается посреди отправки длинной главы.
- Одна и та же Telegram update доставлена повторно.

Ошибки должны логироваться и не приводить к полной потере состояния.

Для временных сетевых ошибок использовать ограниченные повторные попытки с увеличивающейся задержкой.

Постоянные ошибки не должны вызывать бесконечный цикл запросов.

## 18. Тестирование

Использовать автоматические unit-тесты и, где необходимо, интеграционные тесты.

### Обязательные тест-кейсы

**Чтение:**

1. Выбор книги по сокращению.

9. Разбиение длинной главы.

**Ветки:**

11. Статистика учитывается только из привязанной ветки.
12. Сообщения из других веток игнорируются.
13. Админские команды доступны только администраторам.
14. Смена ветки требует подтверждения.
15. Настройки разных групп изолированы.

**Статистика:**

16. Повторная Telegram update не удваивает счётчик.
17. Редактирование сообщения обновляет метрики.
18. `#мысль` считается правильно.
19. `#мысли` не считается.

22. Вопросительное сообщение учитывается один раз.
23. Время сообщения правильно переводится в часовой пояс группы.
24. Номинация «Верные в малом» правильно учитывает 1–7 отчётных дней активности.
25. Сообщения самого бота не учитываются.

**Отчёты:**

26. Формируется топ-3.
27. Правильно обрабатывается равенство результатов.
28. Участники с нулевым результатом исключаются.
29. Отключённая номинация не публикуется.
30. Отчёт не дублируется после рестарта.
31. Ручной отчёт не влияет на автоматический.
32. Не происходит потери или двойного подсчёта событий на границах отчётных периодов.

**Админка:**

33. Кнопки корректно обновляют настройки.
34. Неадминистратор не может выполнять изменяющие действия.
35. Выбор книги через кнопки и через команду даёт одинаковое состояние.
36. Все 66 книг доступны через `/books`.

Тесты, не требующие реального Telegram, выполнять с mock-объектами.

Не выполнять реальные массовые отправки в рабочую группу при автоматическом тестировании.
